# siem-tasks-bot

Python-бот для MaxPatrol SIEM: мониторит статусы задач сбора логов, автоматически перезапускает "упавшие" задачи, следит за потоком событий (EPS) и отдельно — за источниками событий (`event_src.host`) внутри каждой задачи, выявляя источники, переставшие присылать логи. Уведомления и отчёты уходят в Telegram.

## Возможности

- **Мониторинг статусов задач и авто-перезапуск.** Периодически опрашивает `scanner_tasks`, фильтрует по указанной группе задач, уведомляет об изменении статуса и перезапускает задачи в статусах `failed`/`stopped`/`finished`.
- **Мониторинг потока событий (EPS).** Считает количество событий за скользящее окно по каждой задаче, алертит о падении потока (общий и индивидуальные пороги на задачу), поддерживает "тихие часы" и выходные, когда проверка приостанавливается.
- **Мониторинг источников событий.** Раз в несколько часов (только в рабочее время) агрегирует источники (`event_src.host`) внутри каждой задачи через `/api/events/v3/events/aggregation`, копит статистику в SQLite, автоматически чистит её по сроку хранения.
- **Отчёт по "молчащим" источникам.** Раз в сутки строит CSV с источниками, от которых не было событий дольше заданного числа рабочих дней (пн–пт, простой календарь без праздников), и отправляет его в Telegram документом.
- **Сводка "Общая статистика источников".** После каждого цикла сбора статистики в Telegram уходит сообщение с числом источников по каждой задаче (кликабельные ссылки на события задачи в UI MP SIEM) — задачи без данных помечаются отдельно.
- **Диагностические и тестовые режимы командной строки** — см. ниже.

## Требования

- Python 3.9+
- Пакеты: `requests`, `urllib3` (входит в стандартный набор большинства окружений; при необходимости `pip install requests urllib3`)
- Модуль `zoneinfo` (стандартная библиотека Python 3.9+) — для часового пояса "тихих часов"
- PAT-токен MaxPatrol SIEM с доступом к `scanner_tasks` и `events`
- Бот и чат/топик в Telegram (опционально, но без него уведомления не отправляются)

## Установка

```bash
git clone <репозиторий> /opt/siem-tasks-bot
cd /opt/siem-tasks-bot
cp config.ini.example config.ini   # если храните пример отдельно
```

Заполните `config.ini` (см. структуру ниже), затем запустите:

```bash
python3 siem-tasks-bot.py
```

Для продакшена рекомендуется запускать через systemd-юнит с автоматическим перезапуском процесса при падении.

## Структура config.ini

### `[siem]`

| Параметр | Назначение |
|---|---|
| `host` | Хост MP SIEM (без `https://`) |
| `token` | PAT-токен (`Authorization: Bearer <token>`) |

### `[monitor]`

| Параметр | Назначение |
|---|---|
| `group` | Название группы задач для мониторинга |
| `restart` | Перезапускать ли "упавшие" задачи (`true`/`false`) |
| `interval` | Интервал проверки статусов, сек |
| `once` | Выполнить один проход и выйти (для тестов/cron) |

### `[events]` — мониторинг потока событий

| Параметр | Назначение |
|---|---|
| `enabled` | Включить мониторинг EPS |
| `check_interval` | Как часто проверять поток, сек |
| `window_minutes` | Окно расчёта EPS, минуты |
| `min_eps` | Общий порог EPS по умолчанию |
| `custom_taskN` / `custom_eps_taskN` | Индивидуальный порог EPS для задачи с именем `custom_taskN` |
| `quiet_enabled`, `quiet_start`, `quiet_end`, `quiet_skip_weekends`, `quiet_timezone` | "Тихие часы", когда проверка EPS приостанавливается |
| `match_field`, `match_operator`, `match_value_source` | Как событие сопоставляется с задачей (по умолчанию `task_id = <id задачи>`) |
| `repeat_alert_minutes` | Периодичность повторных напоминаний о непрошедшей проблеме (0 — только один раз) |
| `notify_recovery` | Слать ли отдельное уведомление о восстановлении потока |

### `[sources]` — мониторинг источников событий

| Параметр | Назначение |
|---|---|
| `enabled` | Включить мониторинг источников |
| `db_path` | Путь к файлу SQLite со статистикой источников |
| `group_field` | Поле группировки (по умолчанию `event_src.host`) |
| `collect_interval_hours` | Как часто (в часах) собирать статистику |
| `collect_window_hours` | Окно данных для одного сбора, часы |
| `work_start`, `work_end`, `work_days_only` | Рабочее время, в которое разрешён сбор (кроме самого первого запуска — он выполняется сразу) |
| `stale_business_days` | Порог "молчания" источника, рабочие дни (пн–пт) без событий |
| `retention_days` | Срок хранения статистики в SQLite, дальше запись удаляется |
| `report_time` | Время суток, после которого формируется суточный CSV-отчёт |
| `csv_dir` | Папка для сохранения CSV |
| `report_via_telegram` | Отправлять ли CSV в Telegram |
| `fallback_max_pages` | Лимит страниц для запасного (постраничного) сбора, если основной запрос агрегации не сработал |
| `notify_summary` | Слать сводку "Общая статистика источников" после каждого сбора |
| `events_ui_url_template` | Шаблон ссылки на UI MP SIEM для клика по имени задачи в сводке |

### `[telegram]`

| Параметр | Назначение |
|---|---|
| `enabled` | Включить отправку в Telegram |
| `token`, `chat_id` | Токен бота и ID чата |
| `topic`, `topic_id` | Общий топик для уведомлений о статусах/перезапуске |
| `events_topic`, `events_topic_id` | Отдельный топик для алертов о падении EPS |
| `sources_topic`, `sources_topic_id` | Отдельный топик для отчётов и сводки по источникам |
| `no_proxy` | Игнорировать системные переменные окружения прокси при обращении к Telegram API |
| `proxy` | Явный прокси для Telegram (если системный не подходит) |

## Логика работы

1. **Каждые `interval` секунд** — проверка статусов задач и авто-перезапуск.
2. **Каждые `check_interval` секунд** (если `[events] enabled=true`) — проверка потока событий по каждой задаче, с учётом "тихих часов".
3. **Сбор статистики источников** — при первом запуске сразу; далее каждые `collect_interval_hours`, но только в рабочее время. Выполняется в фоновом потоке, не блокируя проверку статусов. После каждого сбора удаляются записи старше `retention_days`, при `notify_summary=true` в Telegram уходит сводка.
4. **Суточный отчёт по молчащим источникам** — после `report_time`, если ещё не отправлялся сегодня. Источники, у которых с последнего события прошло больше `stale_business_days` рабочих дней, попадают в CSV и в Telegram.

Технические детали агрегации источников — через нативный эндпоинт MP SIEM `/api/events/v3/events/aggregation` с PDQL-запросом вида:

```
filter(task_id = "<id>") | select(time, event_src.host, text) | sort(time desc) |
group(key: [event_src.host], agg: COUNT(*) as Cnt) | sort(Cnt desc) | limit(10000)
```

При недоступности этого эндпоинта используется запасной путь — постраничная выгрузка сырых событий с подсчётом источников на стороне бота (ограничена `fallback_max_pages` страницами, чтобы не зависать на задачах с очень большим объёмом трафика).

## Аргументы командной строки

| Флаг | Назначение |
|---|---|
| `--check-events` | Разовая диагностика потока событий по всем задачам группы, без отправки в Telegram |
| `--check-sources` | Разовая диагностика источников по всем задачам группы, без записи в БД и без Telegram |
| `--dump-tasks` | Печатает полный сырой JSON каждой задачи группы (для поиска нужных полей API) |
| `--report-now` | Формирует и **реально отправляет** (CSV + Telegram) отчёт по молчащим источникам на основе уже накопленных данных, не дожидаясь `report_time` |
| `--report-now --stale-days N` | То же, но с временно заниженным/повышенным порогом рабочих дней (без правки `config.ini`) |
| `--report-now --stale-minutes N` | Тестовый режим: источник считается молчащим, если с последнего снимка прошло больше N **минут** реального времени — удобно для проверки отчёта сразу после первого сбора, не дожидаясь смены календарной даты |

## Логирование

Лог пишется только в stdout (без автоматического файла лога на каждый запуск) — при запуске через systemd используйте `journalctl`, либо перенаправьте вывод в файл самостоятельно (`python3 siem-tasks-bot.py >> bot.log 2>&1`).

## Известные особенности API MP SIEM

- Обычный (негруппированный) запрос `totalCount` к `/api/events/v2/events` устойчив к недоступности отдельных источников/конвейеров в кластере Core Events.
- Группировка через `/api/events/v3/events/aggregation` принимает **сырой PDQL-текст** в поле `filter`, а не собранный JSON-фильтр — так был обнаружен и подтверждён через DevTools реальный формат запроса.
- Предупреждение вида `Local sources unavailable: ...` в ответе API не является фатальной ошибкой и не блокирует получение остальных данных.
